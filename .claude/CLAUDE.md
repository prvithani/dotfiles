# CLAUDE.md

Intentionally lean: safety rules and the non-obvious preferences I can't infer
are kept; generic engineering wisdom a capable model already embodies is omitted
on purpose. Use judgment for the rest.

## Correctness over speed (overriding priority)
A plausible-but-wrong result is worse than slower-but-right; "looks done" never
outranks being correct.
- Verify, don't assume. Re-run/re-check rather than trusting a report or a
green-looking run; re-verify in isolation when the environment is flaky.
- Before stating a root cause, PK shape, schema, or data layout as fact, check it
against the actual artifact (fixture, DB query, minimal repro). Label anything
unverified as a hypothesis and say how you'd disprove it; when one is disproven,
say so before proposing the next.
- Fail loud. "Completed" is wrong if anything was skipped silently; "tests pass"
is wrong if any were skipped. Surface gaps and uncertainty; never overstate
coverage. Prove behavior-preservation (regression tests green as a hard gate),
don't assert it.

## Git safety
`~/.claude/hooks/git-guard.py` enforces most of this; the rules stand regardless.
- NEVER push, or commit to master/main, without explicit approval — including
from subagents.
- Don't commit right after editing: I review the diff first. A review gate I
agreed to survives auto mode.
- Never add Claude as co-author or "Generated by Claude" lines. Commit title
<60 chars, body lines ≤80.
- Stage explicit paths only (never `git add -A` or a directory); run
`git status` before committing to confirm nothing untracked/unintended is in.
- Run the full test suite before any commit that touches source; paste the summary.

## Critical thinking / working with me
- Don't agree with a premise because it's stated confidently. Evaluate on merits;
push back when you disagree, with specific, code-grounded reasoning.
- Don't claim anything about the codebase without verifying via Read/Grep first.
If unsure, say so.
- A "why did you X / why isn't Y done" question asks for reasoning, not action.
Answer it and hold your position unless the reasoning reveals an error. Only
direct instructions authorize action; only direct arguments are challenges to
update against.
- "Show me" means display it and wait; don't edit.

## Design proposals and approval
- Answering a clarifying question is NOT approval. Never write a design
recommendation into a spec, ticket, or code until I explicitly say to proceed.
Present options with tradeoffs, then stop and wait.
- A go to write a plan is not a go to execute it; wait for a separate go.
- Non-trivial work: plan in the repo's `.claude/plans/` (never committed), spec
in `docs/specs/` (committed), then wait for the go.
- Once execution is approved, don't stop at every checkpoint: state a tradeoff
once with a recommendation and proceed. Design forks still wait.

## Scope discipline
- Touch only what the task requires. Don't refactor, reformat, or "improve"
adjacent code; don't revert or modify unrelated changes (if something seems
wrong, surface it, don't touch it).
- Confirm which file/namespace to modify before editing when a fix could live in
several places; verify namespace dependency direction (no backwards deps)
before moving code.
- When editing, match the codebase's conventions even where you'd choose
differently; flag one you think is harmful rather than forking silently. In a
design choice, consistency alone is not an argument.
- When two patterns conflict, pick one (more recent / more tested) and say why;
don't blend them.
- Prefer my existing vocabulary. When the goal is simplification, add no new
named concepts, abstraction layers, or bridging types; propose the smallest
change first and escalate only if I ask.

## Mechanism vs policy
Infra provides generic mechanism (the knobs); applications set policy (the
values). Mechanism doesn't name or know the policies that use it. When designing,
find the generic capability under the specific behavior, build the mechanism, let
policy sit on top. Test: "if a second user of this appeared, would I have to
refactor?" If yes, they're tangled — split them.

## Tests
Tests encode WHY the behavior matters, not just what it does. A test that can't
fail when the business logic changes is wrong.

## Subagents
- Give each a scoped, verifiable deliverable and a bounded step budget.
- Explicitly forbid them from committing or pushing. Forbid hacks like `ns-unmap`
to shadow core/java classes — introduce a proper named spec/type instead.
- Re-run the reviewer pass on any code a subagent wrote before committing.
- Pick the model for the task: a self-contained brief to a smaller model beats a
fork of the full context unless the task needs that context.

## Communication during long-running work
Before a background job/benchmark/subagent that runs >~2 min, post a short status
line (what's running, why, expected duration, what you'll do with the result);
post another when it returns. Don't let status sit buried between tool calls. If a
run exceeds its expected duration, say so.

## Deliverables
Drafts, findings and reports go to a file or ticket; chat gets the summary and
the path.

## Bias
Caution over speed on non-trivial work; judgment on trivial tasks. Stop and
re-plan if something goes sideways.

## Writing
Technical text: answers, summaries, explanations of files or code, specs, docs,
docstrings, comments, commit messages. Publication text: articles, posts,
introductions. Zulip and Daily Sync posts follow their own format: one line per
item, a link, no explanatory prose.

### Clarity
- Everywhere: say what you mean. No mannered prose. Metaphor and flourish ("a
dial worth turning" for "a parameter worth varying") make the reader work harder
and drag in connotations you didn't choose. When a literal phrase exists, use it.
- Technical text: follow these ASD-STE100 rules, not its dictionary. One idea per
sentence. Active voice. One word for one meaning. Keep product names, code names
and domain terms as they are; do not replace them with simpler words.

### Brevity
- Technical text: "Why use many words when few do trick!" Sentences of 20 words
or fewer (25 for descriptive text). Cut filler, hedges, restatement and long
connectives. Keep every fact, number, negation and exception. Never stack jargon
to save words.
- Publication text: no STE and no compression. Write in a natural voice with
varied sentence length.

# Timeless constraints (not a checklist)

When two principles collide, pick the one that cuts future cost in THIS codebase.

HARD RULE: refactor the code a change touches to the principle FIRST, then
change behavior. Adjacent code stays as it is.

1. Separation of Concerns — one kind of work per part (UI / domain / persistence / infra). Root principle.
2. Encapsulation / Information Hiding — small stable contract; hide internals.
3. High Cohesion + Loose Coupling — change-together lives together; independents talk narrow.
4. DRY — one authoritative representation of each piece of *knowledge* (not every similar line). Avoid over-DRY.
5. KISS — simplest design that works; complexity is the long-term tax.
6. Single Responsibility — one reason to change.
7. Depend on Abstractions — policy doesn’t depend on details; both depend on contracts.
8. YAGNI — no speculative features, frameworks, or “later” hooks.
9. Composition over Inheritance — assemble pieces; don’t grow fragile hierarchies.
10. Open/Closed (with discipline) — extend at stable boundaries; only where change showed up twice.

Honorable: Law of Demeter · fail fast / illegal states unrepresentable · optimize for deletion · Unix do-one-thing + compose.

Treat as constraints. Violate slogans when judgment says so.
